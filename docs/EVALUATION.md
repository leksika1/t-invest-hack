# Оценка качества: инструмент и протокол

Инструмент этапа 5 реализован в `backend/eval/`. Эксперимент качества реальной LLM на 30–50 выпусках **ещё не проведён**. В репозитории есть два синтетических контроля и два непроверенных черновика реальных демо-выпусков. Их нельзя выдавать за размеченный test-корпус или за достигнутые показатели модели.

## Что реализовано

- Gold JSON: ровно 15 кодов из CARD_FIELDS, типы value из Pydantic бэкенда, допустимые альтернативы, атомарные условия, цитаты/физические страницы, SHA256 PDF, снимок ISS, происхождение и проверяющие.
- Валидатор формата, файлов и цитат. Повторные JSON-ключи, NaN/Infinity, неизвестные поля/статусы, отсутствие PDF, неверный sha256 и несуществующая эталонная цитата — ошибка входа, а не 100% результата.
- Чтение полных карточек из JSON или через GET API стенда. CLI не создаёт карточки, не меняет документы, не вызывает модель и не требует admin/LLM ключа.
- Regex/keyword baseline по тем же выбранным PDF и тому же снимку ISS. Он не читает ожидаемые ответы gold; ISS используется только для сверки, а не для заполнения отсутствующего документного ответа.
- Парные Markdown/JSON отчёты, таблица «конвейер / LLM vs baseline», абсолютные знаменатели и ошибки, отдельные результаты ISS-only, расходы/время и PASS/FAIL.

Живой ISS, discover/download и разбор четырёх PDF проверены 15.11.2026. Файлы/страницы/источники/время захвата находятся в `eval/data/demo`, SHA и origins — в gold. Источники: [ISS Балтийского лизинга](https://iss.moex.com/iss/securities/RU000A10ATW2.json), [ПРАЙМ](https://disclosure.1prime.ru/Portal/Default.aspx?emId=7826705374), [ISS Аэрофлота](https://iss.moex.com/iss/securities/RU000A10CS75.json), [СКРИН](https://disclosure.skrin.ru/disclosure/7712040126/6).

Снимки содержат доступные значения 6 из 8 стандартных полей. Тип купона в этом снимке не размечен как явный факт ISS; оферты не возвращены как события. Это не доказательство отсутствия оферты и не основание выводить юридический тип купона по ставкам. Поля сохранены как TODO/unscorable. Нормализованные значения зафиксированы вместе с raw ISS и не пересчитываются при оценке новым кодом нормализации.

В реальных PDF размечены номинал и дата размещения, выдержки о погашении по требованию владельцев/call и явное отсутствие обеспечения. В Балтийском лизинге также зафиксированы окно требований о приобретении и дата досрочного погашения 13.02.2028 из условий размещения; в Аэрофлоте — плавающий тип купона и формула K + S с правилом наблюдения и TODO по величине S. Частично описанные условия остаются unscorable с TODO: оба решения ссылаются на программы, а программы не входят в найденные два PDF на выпуск. Ковенанты/кросс-дефолт/ограничения нельзя объявлять отсутствующими без полного комплекта. Ни один реальный черновик не допущен к первичным метрикам.

## Подготовка нового gold

1. Собрать полный комплект нужной редакции: решение, программа/проспект, изменения, решения о ставках/оферте и необходимые сущфакты. Зафиксировать enabled, тип, источник, source/download URL, опубликовано (nullable) и получено. Положить неизменяемые PDF в `eval/data/<isin>/`.
2. Сохранить сырой ISS description/emitter/search/bondization и нормализованные `fields`, ISIN, URL и fetched_at. Формат снимка: `{"isin":"RU...","fetched_at":"...","fields":{},"raw":{}}`; поля реально заполняются, `{}` не заменяет отсутствующий сбор. См. сохранённые `data/demo/.../iss.json`. Для live-захвата двух демо есть отдельный явный CLI ниже.
3. Скопировать [полный шаблон](../backend/eval/templates/gold.json) в `eval/gold/dev/<isin>.json`. [JSON Schema](../backend/eval/templates/gold.schema.json) описывает структуру; runtime-валидатор дополнительно проверяет ровно 15 кодов, типы value, атомы и файлы. В document.path/iss_fixture использовать пути **от assets-root**, не от самого gold. Абсолютные пути и выход через `..` запрещены.
4. Для каждого PDF посчитать SHA256: `python -c "import hashlib,pathlib; print(hashlib.sha256(pathlib.Path('eval/data/ISIN/decision.pdf').read_bytes()).hexdigest())"`. Выбрать стабильный document_id. Он не обязан совпадать с UUID бэкенда: сопоставление карточки с gold идёт по sha256.
5. Первый разметчик заполняет все 15 полей и все отдельные условия массивов. Второй независимо проверяет **все** значения, цитаты, исключения, отрицания, сроки, цены, субъекты и актуальность. Разногласия сохраняются в review.disagreements; арбитр записывает adjudicator/resolution. Два разных annotators, resolved=true, needs_human_check=false и отсутствие TODO обязательны для допуска. Пользовательские confirmed/corrected — только материал для разметки после такой проверки.
6. Разметить `not_found` только как отсутствие в **данном полном выбранном корпусе**, с reason. Явный отказ от обеспечения/опции можно подтвердить отрицательной цитатой. Неопределимая редакция, битый/неполный PDF — `unscorable: true` с причиной, не not_found. Исключения публикуются; строгий PASS этого инструмента требует закончить/устранить их, а не уменьшить знаменатель незаметно.
7. Добавить выпуск в manifest с split, issuer_group и относительным gold-путём. Предлагаемое разбиение: 30% dev / 70% test, целыми эмитентами; seed и состав опубликовать. Один issuer_group в двух частях валидатор запрещает. Заморозить модель, prompt/schema/baseline версии, top-k, пороги, embedding режим и тарифы до test. Не настраивать словари/aliases на test.
8. После сборки карточки на выбранном комплекте записать её card_id в manifest. Это фиксирует версию для API-оценки. При null CLI явно выбирает последнюю карточку, сохраняет ID/версию в отчёте и `--save-cards`; для приёмочного эксперимента использовать закреплённые ID.

Для сканов положить неизменяемый sidecar страниц: `{"pdf_sha256":"...","pages":[{"number":1,"text":"...","ocr":true,"error":null}]}` и его SHA в pages_file/pages_sha256. Для текстовых PDF оценщик читает текст непосредственно из PDF и проверяет совпадение с sidecar, если он есть. Неуспешный OCR не превращается в пустой правильный ответ. OCR-текст требует проверки человеком.

### Поле и атомарные условия

`value` соответствует [CARD_FIELDS](CARD_FIELDS.md) и backend schema.py. Десятичные числа — строки, даты — ISO. Для положительного ответа нужны quote/document_id/page/expected_status. Для полей 1–8 iss_value обязан совпадать с зафиксированным ISS snapshot, а expected_status — с нормализованной сверкой. Реальный mismatch размечается как правильный флаг **и оба значения**, не как приоритет документа над ISS.

Рисковые массивы имеют atom на каждый индекс. Один atom — одно условие; `condition_id` стабилен в выпуске. category: covenants/call/early_redemption/put/other. Если одна put-опция описана в offers и offer_procedure, задайте одинаковый condition_id: категория считает его один раз и требует корректности всех размеченных представлений. Для массивов основная цитата относится к элементу 0, evidence.value_path — к остальным (`/items/1`, `/events/1`, `/payments/1` и т. п.).

Пример правил одного atom (это фрагмент, не полный gold):

```json
{"index":0,"condition_id":"leverage-1","category":"covenants","alternatives":[],"constraints":{"condition":[["долг","задолженность"],["EBITDA"],["не более"]]}}
```

Группы constraints соединяются AND, варианты внутри группы — OR; путь ведёт к текстовому слоту атома, например `threshold.currency`. Без правила применяется нормализованное равенство всех непустых слотов. Для перефразирования можно задать заранее одобренные полные alternatives атома/поля. Числа, операторы «более/менее», отрицания и исключения правилами не игнорируются. Утрата отдельного непустого слота — ошибка. Это детерминированный ограниченный matcher, **не универсальная смысловая экспертиза**; все TP реального малого корпуса проверяются человеком. Добавлять альтернативу после просмотра ошибок test без нового разделения нельзя.

## Метрики и приёмка

| Метрика | Расчёт / поведение | Порог |
|---|---|---|
| Accuracy стандартных полей | Правильные / все оцениваемые пары выпуск–поле 1–8. Нужны документное value, источник/цитата и верный машинный статус. Для mismatch — также правильное iss_value. Gold not_found учитывается. Отсутствующая карточка/поле остаётся ошибкой в знаменателе | ≥95% |
| Recall/precision рисковых полей | Максимальное взаимно-однозначное сопоставление атомов: TP/(TP+FN), TP/(TP+FP). Дубликаты не повышают recall и дают лишний FP. Неверное значение, неподтверждённая цитата или пропуск — не TP | Публикуются по всем 7 полям, micro и macro |
| Категории приёмки | covenants, call, early_redemption, put и их объединение; condition_id не считается дважды | ≥85% **в каждой** категории и объединении |
| Показанные неподтверждённые значения | Видимый машинный value с неверной/отсутствующей документной цитатой. Честный extracted/moex_iss сверяется со snapshot и учитывается отдельно | 0 |
| Показанные неверные значения | Значение/атом не соответствует gold, включая утрату исключений. Правильная цитата сама по себе не доказывает правильность значения | 0 — дополнительная строгая проверка |

Нормализация: Decimal-строки/валюты, ISO-даты, порядок массивов, развёртка купонных диапазонов. Формула не равна одной ставке; недостающие параметры не принимаются за нули. Сравнение с полным gold строже частичной сверки наблюдаемого ISS: нельзя подтвердить весь график по одной строке.

Скрытый needs_review — FN на положительном gold; показанный needs_review не даёт TP, но проверяется на галлюцинации. Отдельно публикуются needs_review, not_found, coverage, TN отрицательных полей и ignored human edits. Review/not_found отсутствующих условий не позволяет пройти положительные категории. Для нулевого знаменателя — **N/A**, не 100%; категория N/A не проходит порог. Semantic- и citation-счётчики могут пересекаться; total hallucinations — их объединение, а не сумма.

ISS-only режим оценивается отдельно: прямые биржевые значения могут быть верны, но не доказывают извлечение из PDF и не дают победы над baseline. Значение из источника moex_iss исключается из PDF-галлюцинаций только при extracted, отсутствии фиктивной цитаты и совпадении с ISS snapshot.

`status=PASS/FAIL` относится к порогам выбранного набора и полноте сравнимых входов. `mvp_quality_status=PASS` дополнительно требует замороженный **реальный** корпус 30–50 выпусков, проверенную разметку, запуск на всей test-части manifest и прохождение порогов. Синтетика никогда не доказывает качество MVP. Черновики/unscorable публикуются в exclusions и блокируют строгий PASS.

## Запуск

Все команды ниже — из `backend`, с установленными requirements-dev. На Windows Python из проекта: `.venv/Scripts/python.exe -X utf8`. При запуске CLI без аргументов/с `--help` модель не вызывается.

### Проверка поставляемых файлов и синтетический smoke

```bash
python -m eval.validate --gold eval/gold --manifest eval/manifest.json
python -m eval.baseline --gold eval/gold/synthetic --manifest eval/manifest.synthetic.json --output eval/artifacts/baseline-cards.json
python -m eval.run --gold eval/gold/synthetic --manifest eval/manifest.synthetic.json --split test --cards eval/examples/synthetic-cards.json --baseline-cards eval/artifacts/baseline-cards.json --label "Synthetic oracle (not LLM)" --output eval/artifacts/synthetic.md
```

Вместо отдельного baseline-файла можно передать `--with-baseline`: он будет построен из тех же PDF/ISS. Сохранённый [пример отчёта](../backend/eval/examples/synthetic-report.md) и его JSON сравнивают **oracle контроль**, а не реальную LLM: 16/16 standard, 13 TP/0 FP/0 FN; baseline — 15/16, 11 TP/1 FP/2 FN. Oracle PASS проверяет механику; `mvp_quality_status` остаётся FAIL. Эти числа не являются измеренным качеством MVP.

Негативный контроль (завершается кодом 1):

```bash
python -m eval.run --gold eval/gold/synthetic --manifest eval/manifest.synthetic.json --cards eval/examples/negative-cards.json --label "Synthetic fault injection (not LLM)" --output eval/artifacts/negative.md
```

В [negative-cards](../backend/eval/examples/negative-cards.json) намеренно выдумана одна цитата call-условия. Она должна дать FAIL и ненулевой hallucinations_without_citation. Файлы синтетики воспроизводимы: `python -m eval.synthetic --output-root eval` перегенерирует только synthetic PDF/gold/oracle/negative и manifest.synthetic, реальные черновики не меняет.

### Против Dev и локальной выгрузки

Сначала человек собирает карточки в UI с тем же комплектом PDF; оценщик выполняет только GET:

```bash
python -m eval.run --gold eval/gold/demo --manifest eval/manifest.json --split dev --base-url https://dev.tinvest.leksika1.ru --save-cards eval/artifacts/dev-cards.json --with-baseline --output eval/artifacts/dev.md
python -m eval.run --gold eval/gold/demo --manifest eval/manifest.json --split dev --cards eval/artifacts/dev-cards.json --with-baseline --output eval/artifacts/dev-offline.md
```

Для реального принятого test-корпуса заменить gold/manifest на свои файлы и передать `--split test`. JSON-вход — массив полных ответов GET /api/cards/{id} либо `{cards:[...]}`, одна выбранная версия на ISIN. Markdown-экспорт UI не является входом оценщика. DB-данные можно выгрузить в тот же формат; прямой доступ CLI к БД не требуется.

Коды: **0** — пороги основного прогона PASS; **1** — отчёт создан, пороги/полнота FAIL; **2** — ошибка входа/файлов/API. Ошибка не становится пустым отчётом PASS. Отсутствующие поля/карточки JSON считаются ошибками/FN; ошибочный формат отвергается. Если команда завершилась кодом 2, не использовать старый файл отчёта как результат нового запуска.

При живой read-only проверке 15.11.2026 Dev не вернул карточку RU000A10ATW2: команда остановилась без job/модели. Поэтому сравнение **реального** конвейера с baseline на Dev здесь не выполнено.

### Повторный live capture двух демо

```bash
python -m eval.capture --output-root eval/artifacts/new-capture --max-documents 2
```

Команда использует только существующие ISS/коллекторы и PDF parser, не модель/БД. При повторе в уже занятый каталог gold она откажется перезаписывать ручную разметку. PDF/raw ISS/pages/sha и черновики будут под новым output-root; для включения в корпус их нужно проверить и добавить в manifest. В поставленных заготовках выбраны оба найденных документа на выпуск; это **не означает полный комплект** — программы/изменения нужно проверить отдельно. При сетевой/robots/OCR ошибке сохраняется TODO/ошибка, а не фиктивные факты. HTTP-кэш и рабочие отчёты игнорируются через eval/.gitignore.

## Как читать отчёт

Сначала смотреть статус основного прогона, тип/размер корпуса, split, exclusions и mvp_quality_status. Затем таблицу конвейера/baseline, знаменатели ISS, TP/FP/FN по 7 полям и категории приёмки. В JSON сохранены результаты каждого поля, документ/page ошибки, состав/sha PDF и gold/manifest/ISS, actual models из журналов, выбранные card_id/version, настройки и состояния коллектора.

Стоимость `null` означает неизвестность, известная часть показана отдельно. Токены/usage и списания считает шлюз; оценщик не объявляет недостающий журнал бесплатным. Время конвейера берётся из build-job и не включает предыдущий ingest; время baseline — локальное извлечение после чтения корпуса. Это не равные end-to-end замеры OCR/сетей. Oracle имеет нулевые фиктивные стоимость/время как контроль, не как измерение модели.

Автосбор precision/recall, OCR accuracy и retrieval recall без отдельной эталонной разметки публикуются как N/A. Успешный discover/download не доказывает полноту; collection.complete_corpus, источники/ошибки и ручной путь сохранены. Разбивки по scans/text, типам купона и группам эмитентов следует добавлять на реальном замороженном корпусе, не делать выводы о распределении по двум синтетическим примерам.

## Гипотеза и незавершённый эксперимент

Гипотеза: RAG + LLM с проверками лучше regex на неоднородных юридических условиях, сохраняя точность/источники. Для её проверки нужны одинаковые документы/ISS и два независимых разметчика с арбитражем. Основная исходная модель — google/gemini-2.5-flash через OpenRouter; в отчёте фиксируется фактически вызванная модель. Платный эксперимент запускается отдельно владельцем с настроенным шлюзом/бюджетом, не оценщиком.

Текущий результат — готовый инструментарий и проверенные контроли, а не подтверждение гипотезы. Полный test-корпус 30–50 реальных выпусков, показатели модели и приёмка качества ещё отсутствуют.
