# План разработки

Этапы 1/1b — документация и её уборка: README, docs, перенос анкеты в contest; в workflow/корневом Compose актуализированы только комментарии со ссылкой на инструкции деплоя. Ограничение «код/тесты/зависимости не меняются» относилось только к этапам 1/1b. Этапы 2–4 и инструментарий этапа 5 реализованы; фактические проверки описаны в конце документа. Качество реальной модели на корпусе 30–50 выпусков не подтверждено. Уточнения отдельных brief имеют приоритет над мастер-заданием; `.env*` и `.git` не редактируются.

## Текущее состояние и будущая структура

После этапа 3 schema.py содержит SPECS/FIELDS: 15 типизированных значений вместо 16 прежних полей. POST /api/cards — асинхронный 202. Обработчик build_card, gateway, prompts, retriever, verification, export, admin и DB rate limiter реализованы; прежние routes health/ISS/issues/documents сохранены.

Предлагаемая структура (существующие каталоги сохраняются; новые добавляются по этапам):

```text
backend/
  alembic/                 миграции и расширения (этап 2)
  app/
    models/                сущности SQLAlchemy
    issues/                выпуск, snapshot ISS, маршруты
    iss/                   клиент + маппинг и нормализация
    documents/             DocumentSource, upload, PDF/OCR, хранение/provenance/выбор
      sources/             PrimeSource, SkrinSource, официальный EDisclosureSource
    indexing/              chunks, FTS, optional embeddings
    jobs/                  таблица, worker, lease, progress
    llm/
      client.py            транспорт существующего клиента
      gateway.py           бюджет, журнал, ретраи
      prompts/             русские промпты по полям
    cards/                 схема 15 полей, retrieval, extraction, verification, export
    admin/                 защищённый журнал и stats
  tests/                   unit, PostgreSQL-интеграционные, e2e/
  eval/                    run, baseline, gold, manifest (этап 5)
frontend/src/              поток загрузки/прогресса/карточки (этап 4)
```

Имена новых модулей — проектное предложение, контрактом являются ответственность и поведение. Схема полей/подсказок остаётся единой для валидатора, извлечения, UI и оценки. Файлы промптов должны попадать в backend-образ.

## Этап 2 — данные и фоновая обработка

Работа:

- Alembic и таблицы из ARCHITECTURE; индексы/уникальности, vector-расширение. Миграции перед Uvicorn; не заменять их `create_all`.
- ISS: ISIN → secid → эмитент/ИНН, description + полный bondization, fixtures, нормализация дат/валют/Decimal, маппинг 1–8/шапки. На этапе 2 подтверждено EMITTER_ID → emitters/{id}.emitter.INN, fallback emitent_inn; JSON сохранён в fixtures. Отсутствующие поля не домысливать.
- `DocumentSource`: PrimeSource → SkrinSource → официальный EDisclosureSource по ИНН/названию. Структуры страниц ПРАЙМ/СКРИН проверены на этапе 2; robots, контактный User-Agent, задержки, retry/кэш, PDF/архивы, sha256 и несколько origins одного PDF — DATA. AK&M не использовать; не обходить капчу/403 Интерфакса.
- EDisclosureSource на этапе 2 сначала реализовать как заглушку «нужен официальный доступ»: без EDISCLOSURE_API_URL/KEY выключен; с env до реализации договорного адаптера — adapter_not_implemented. Проверить официальный API при получении доступа, не выдумывать его методы. Ассистированный режим обязателен: проверить URL поиска e-disclosure по ИНН, формировать ссылку/запрос и предложить ручную загрузку. Готовность MVP допускает заглушку официального API, если доступ ещё не предоставлен, при честном статусе и рабочем ручном пути.
- Загрузка PDF доступна независимо от коллекторов/ISS; безопасный путь, лимит 30 МиБ, volume, страницы PyMuPDF/Tesseract rus+eng. Архивы только из разрешённых источников, ограниченная безопасная распаковка; путь/SSRF/redirect/zip-bomb проверки.
- Нарезка по страницам/пунктам, FTS russian; nullable embeddings через шлюзовую абстракцию. На этом этапе разрешён только fake/выключенный embedding endpoint до готовности бюджетного шлюза этапа 3; прямых платных вызовов в обход шлюза нет.
- Jobs + asyncio-worker, захват/lease, прогресс/ошибки, идемпотентность/восстановление; API collect/documents/issues/jobs, PATCH enabled. Состояния источников отдельно от парсинга и job; активный collect не плодит новые задачи. Выбор пользователя сохраняется при повторе.
- Согласованные изменения backend Dockerfile, корневого и backend Compose (новые env и files-volume). Если проверки меняются — обновить и `scripts/ci.sh`, и workflow, добавить PostgreSQL в CI интеграционных тестов.

Готовность: миграции на пустой БД и повторный запуск успешны; PDF после рестарта сохранён; дубли не множатся, все origins видны. ПРАЙМ/СКРИН исследованы и их реальный поиск/загрузка проверены отдельным smoke с разрешённым доступом (не ежедневная зависимость CI); mock HTML/robots/PDF/архивы покрывают 403, запрет robots, 429, таймаут, чужого эмитента/выпуск, дубликаты и опасную распаковку. Порядок источников, частичный результат, disabled официальный Интерфакс и ассистированная ссылка проверены. Без автосбора пользователь может загрузить PDF и получить список; выключенный документ не попадает в snapshot и не блокирует его, повторный collect не включает его обратно.

Русские страницы/сканы и пустой OCR имеют явные статусы. FTS работает без embedding-конфига/при его ошибке. PostgreSQL-тесты проверяют реальные FTS/vector и конкурентный захват, не SQLite. Unit-тесты без сети; сбой ISS и неполный график отдельно. Невозможность Docker/живого smoke фиксировать как непроверенное, не как готовый коллектор или деплой.

Стоимость: usage.cost (включая 0) приоритетна, иначе тарифы конфига; хранить источник стоимости и usage. Проверить обе ветки и неизвестный расход. Для эмбеддингов не настроено/ошибка → FTS.
- Промпты на русском, retriever FTS/vector с ограничением snapshot, экстракция и проверка цитат всех составных элементов. Нормализация и сверка ISS — правилами; плохая цитата → скрытое value и review.
- Деградированный режим без ключа: ISS-only extracted, рисковые not_found с причиной; исчерпание бюджета отдельно. Запись карточки/журнала и snapshot только выбранных документов с origins, PATCH, Markdown, admin с compare_digest, rate limits (включая collect).

Готовность: FakeLLM по коду поля + синтетический PDF с русским текстом (создаваемый PyMuPDF в тесте) воспроизводят ковенант, call и оферту с цитатами. Есть проверки ложной цитаты, чужой страницы/документа, изменения числа/отрицания, низкой уверенности, реального mismatch, пропуска условия, неполного графика и конфликтов версий. Невалидный JSON/429/5xx/timeout/бюджет не приводят к непроверенному ответу. Параллельные запросы не обходят бюджет. Admin без токена закрыт; правки сохраняют исходные результаты.

Обновить unit и `tests/e2e`: без ключа LLM загрузить PDF → дождаться ingest → собрать карточку → дождаться job → проверить 15 полей, ISS-only статусы и рисковые not_found, экспорт и сохранённую правку. Для воспроизводимого ISS-сценария использовать тестовый mock HTTP ISS endpoint/записанные JSON в изолированном e2e-окружении; живой ISS — отдельный smoke, не обязательная сетевая зависимость CI. Для детерминированной no-key e2e LLM-ключ должен быть пустым даже в окружении с ключом разработчика.

Затем разбор, сборка, polling job, последние карточки. Готовность: `npm run lint`, `npm run typecheck`, `npm run build` проходят; вручную пройден весь поток, включая загрузку/ошибку, восстановление карточки после перезагрузки, исправление и экспорт. Проверены клавиатура, читаемость без различения цветов, узкий экран, длинные цитаты/таблицы. Подтверждение/исправление не подменяют машинный статус, повтор POST не запускается автоматически при polling. В nginx проверены CSP и согласованный multipart-лимит. Результаты визуальной проверки фиксируются отдельно от backend e2e.

## Этап 5 — оценка

Инструментарий реализован; фактическая передача и проверки — в конце документа. Приёмка качества реальной модели остаётся незавершённой.

Работа: `backend/eval/`, валидатор gold, regex/keyword baseline, CLI оценки, Markdown-отчёт и 1–2 синтетических эталона с воспроизводимыми PDF/ISS. Реальный корпус и эксперимент по [EVALUATION.md](EVALUATION.md) собираются отдельно командой, не объявляются существующими.

Готовность инструментария: CLI детерминированно считает TP/FP/FN, accuracy, recall/precision, неподтверждённые показанные ответы, исключения и coverage; тестовый пример с намеренно ложной цитатой проваливает критерий нуля галлюцинаций, пропуск снижает recall. Ошибочные/несовместимые входы не превращаются в отчёт 100%.

Готовность качества MVP: на замороженном test 30–50 выпусков (общий корпус) опубликованы split и знаменатели, ≥95% accuracy ISS-полей, ≥85% recall ковенантов/опционов и 0 ответов без подтверждения; есть сравнение baseline, время/стоимость и анализ ошибок. Если корпус не собран или пороги не достигнуты — инструментарий можно завершить, но качество MVP остаётся неподтверждённым. По итогам обновить документацию с фактическими числами.

## Проверки и доказательства готовности

Команды установки/запуска unit, e2e, frontend, полного CI и хуков находятся в [OPERATIONS](OPERATIONS.md), чтобы не поддерживать две копии инструкций. На этапах 1/1b тесты приложения не запускаются. Проверки новых возможностей перечислены в критериях этапов выше; несуществующие пока pytest-маркеры/пути не объявляются готовыми командами.

Будущие интеграционные тесты работают с отдельной PostgreSQL/pgvector БД через DATABASE_URL, никогда Dev/PROD; при их добавлении изменить оба CI-пути согласованно. FakeLLM/ISS/коллекторы используют локальные fixtures. E2E без ключа LLM не должны случайно наследовать ключ разработчика; проверять выбранные документы и origins наряду со статусами полей. Live smoke коллекторов проводить отдельно от unit/CI с соблюдением robots, задержек и разрешённого доступа; записывать дату и фактический результат.

Оценка качества — отдельный запуск [EVALUATION](EVALUATION.md), не существующий CI-шаг. В конце каждого этапа указывать реально выполненные команды и результаты, отличая статическую проверку, unit/интеграционные, e2e, живые источники и Dokploy.
