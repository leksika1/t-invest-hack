# Ответы на задачи 4–8. «Карточка облигации» (ядро «Облигационного монитора»)

## Задача 4. Как будет работать решение?

Аналитик долгового рынка или инвестсоветник вводит ISIN биржевой корпоративной облигации (приоритет — ВДО). Агент сам находит на e-disclosure.ru решение о выпуске, проспект и сущфакты, извлекает текст из PDF (для сканов — OCR), режет на фрагменты и индексирует. LLM по JSON-схеме заполняет ~15 полей: номинал, купоны, оферты, амортизацию, а также ковенанты, основания досрочного погашения, call-опцион, поручительство, кросс-дефолт, порядок участия в оферте. К каждому полю — цитата и ссылка на страницу или пункт. Поля, которые есть в MOEX ISS, сверяются с биржевыми данными. Результат — карточка выпуска с флагами «расхождение с ISS», «не найдено», «требует проверки»; поле без цитаты не показывается. Аналитик проверяет флаги по ссылкам и использует карточку в анализе. Следующее действие — решение о включении выпуска в shortlist или в материалы для клиента либо вопрос эмитенту или организатору. Рекомендаций купить или продать система не даёт.

(949 символов)

## Задача 5. Что именно будет делать AI?

AI извлекает из эмиссионных документов текстовые условия выпуска: ковенанты, основания досрочного погашения, call-опцион, поручительство, кросс-дефолт, порядок участия в оферте — с цитатой к каждому. Документы не унифицированы: одно условие сформулировано по-разному, разбросано по разделам, со ссылками на другие пункты и исключениями («кроме случаев…»). Regex ломается при смене юрфирмы-составителя, поиск по словам находит фрагмент, но не понимает смысл. Без AI: стандартные поля берём из MOEX ISS, сравнение и флаги делают правила. AI лишь приводит даты и параметры из текста к полям ISS, чтобы их можно было сверить.

(621 символов)

## Задача 6. Какие AI-подходы планируется использовать?

Отмечаем: **LLM; RAG; AI-агент.**

Текст для дополнительного поля:

LLM извлекает поля по JSON-схеме и понимает формулировки с отсылками и исключениями. RAG находит нужные фрагменты в документе на десятки страниц и даёт цитату со страницей, поэтому каждое поле можно проверить. AI-агент сам находит документы выпуска по ISIN и сверяет поля с MOEX ISS. OCR для сканов — готовый инструмент предобработки, а не основа решения.

(355 символов)

## Задача 7. Технический контур MVP

**Поток:** ISIN → агент-сборщик (e-disclosure.ru, MOEX ISS) → разбор PDF / OCR → фрагменты + индекс → LLM-извлечение по схеме → сверка с ISS → карточка с цитатами и флагами → проверка человеком.

**Компоненты**
- Интерфейс: Telegram-бот или простая веб-форма. Вход — ISIN; вторым приоритетом — загрузка своих PDF.
- Агент-сборщик: по ISIN находит эмитента и выпуск, скачивает решение о выпуске, проспект, изменения к ним и сущфакты; по ISS получает параметры выпуска.
- Разбор документов: текстовый слой PDF (pdfplumber / PyMuPDF), для сканов — OCR; нарезка на фрагменты с сохранением страницы и номера пункта.
- Индекс: гибридный поиск (векторный + по ключевым словам) по фрагментам выпуска.
- Извлечение: для каждого из ~15 полей RAG подбирает фрагменты, LLM возвращает JSON по схеме: значение, цитата, страница/пункт.
- Сверка (правила, без AI): ~8 полей сравниваются с ISS; цитата проверяется на точное наличие в тексте документа. Нет цитаты — поле скрыто; расхождение — флаг вместо ответа.
- LLM-шлюз: все вызовы модели идут через один шлюз с дневным лимитом расходов, журналом запросов и ошибок (ошибки видны в админке). Модель за абстракцией и переключается без переделки конвейера.

**Модели** (выбор подтвердим на тестовой выборке)
- Основная LLM: облачная модель с structured output из российского контура (GigaChat или YandexGPT) или зарубежная через шлюз.
- Альтернатива для закрытого контура: open-weight модель (например, семейство Qwen) на своём сервере.
- Эмбеддинги: мультиязычная модель (bge-m3 или multilingual-e5).
- OCR: Tesseract или PaddleOCR; облачный OCR как вариант. Качество на русских сканах проверить.

**Хранилища**
- PostgreSQL + pgvector (или Qdrant): фрагменты, эмбеддинги, карточки, история версий документов.
- Файловое / S3-хранилище: исходные PDF.
- Журнал: вызовы LLM, расходы, ошибки, правки человека — для оценки качества.

**Внешние API и инструменты**
- e-disclosure.ru / Интерфакс-ЦРКИ — эмиссионные документы и сущфакты (условия автоматического доступа проверить).
- MOEX ISS: /iss/securities/{secid}.json (параметры выпуска), /iss/securities/{secid}/bondization.json (купоны, оферты, амортизация).
- API выбранной LLM.

**Результат работы системы**
Карточка выпуска (в боте, Markdown или PDF): ~15 полей, у каждого значение, цитата, ссылка на страницу/пункт и статус: «сверено с ISS», «расхождение с ISS», «не найдено», «требует проверки». Это факты из документов, а не ИИР. В MVP нет скоринга, рекомендаций, рассылок и мониторинга в реальном времени.

**Развитие** (не входит в MVP): тот же конвейер даёт календарь корпоративных событий, затем «что изменилось» между версиями документов и ранние сигналы ухудшения эмитентов ВДО. Любой AI-текст, который пойдёт инвестору, сначала проходит фильтр на признаки ИИР.

## Задача 8. Какие данные потребуются?

**1. Эмиссионные документы** (решение о выпуске, проспект, изменения к ним)
- Источник: e-disclosure.ru / Интерфакс-ЦРКИ, сайты эмитентов.
- Формат: PDF (текстовый слой или скан), иногда DOC/HTML.
- Обновление: по событию — при размещении и внесении изменений.
- Ограничения: часть документов — сканы без текстового слоя; несколько версий документа, нужно выбирать действующую; у части эмитентов раскрытие урезано или ограничено.

**2. Сообщения о существенных фактах**
- Источник: e-disclosure.ru / Интерфакс-ЦРКИ.
- Формат: полуструктурированный текст (HTML/PDF) с типом сообщения.
- Обновление: ежедневно по эмитентам из выборки.
- Ограничения: параметры событий (оферта, изменение ставки) — в свободном тексте; раскрытие части эмитентов ограничено.

**3. Данные MOEX ISS**
- Источник: ISS API (/iss/securities/{secid}.json, /iss/securities/{secid}/bondization.json).
- Формат: JSON.
- Обновление: ежедневно.
- Ограничения: в бесплатном доступе часть данных отдаётся с задержкой или ограничениями (условия проверить); для карточки нужны справочные параметры, а не котировки в реальном времени. ISS даёт стандартные поля и не содержит ковенантов.

**4. Справочник эмитентов и выпусков**
- Источник: MOEX ISS (ISIN, secid, эмитент, ИНН), карточки эмитентов на e-disclosure.
- Формат: JSON / таблица.
- Обновление: ежедневно или при новых размещениях.
- Ограничения: связку «ISIN → эмитент → страница раскрытия» придётся строить и проверять самим.

**5. Эталонная разметка для оценки**
- Источник: ручная разметка командой 30–50 биржевых корпоративных выпусков, включая ВДО; для ~8 полей эталон — MOEX ISS.
- Формат: таблица (CSV/JSON): поле, значение, цитата, страница.
- Обновление: один раз перед MVP, затем пополнение по правкам пользователей.
- Ограничения: готового размеченного корпуса нет; разметка текстовых условий трудоёмка и требует второго проверяющего.

**6. Агрегаторы для сравнения (опционально)**
- Источник: Cbonds, Rusbonds, карточки на сайте Мосбиржи.
- Формат: веб-страницы / API по подписке.
- Обновление: по мере проверки.
- Ограничения: платный доступ и лицензии на использование данных. Нужны только для проверки предположения о неполноте рисковых условий (первый шаг — 10 выпусков ВДО).

**7. Кредитные рейтинги (задел на развитие)**
- Источник: пресс-релизы АКРА, Эксперт РА, НКР, НРА.
- Формат: HTML/PDF.
- Обновление: по событию.
- Ограничения: в MVP не используются; условия повторного использования проверить.

**Что знаем и что предполагаем.** Знаем: эмиссионные документы и сущфакты публичны, структура ISS известна. Предполагаем, что доля сканов и урезанного раскрытия невелика. Это проверим на выборке до разработки.
